# 2026-10-03 — Fase 8: plan Pro

- Autor: Claude Sonnet 5.5
- Duración aprox: sesión larga (spec, ADR, backlog y las siete tareas)

## Objetivo

El usuario cambió la monetización: dos planes, Free y Pro, y lo único que los diferencia es poder
ver las estadísticas. Los dos cargan todos los ejercicios y marcas que quieran. Pidió además:

- Ver en el perfil qué plan se tiene.
- Una sección para gestionar la suscripción (plan actual, lo que se paga, pasar de uno al otro),
  **sólo UI** por ahora: la pasarela de pago es una segunda etapa.
- Un indicador en el header que diga que se tiene Pro.

## Decisiones tomadas

- **"Estadísticas" es todo lo de `stats`** (elegido por el usuario): la pantalla completa, por
  ejercicio y generales, y el progreso del detalle. Free sigue viendo valor actual, mejor marca,
  porcentajes e historial. Opciones descartadas: dejarle las generales, o dejarle el progreso del
  detalle.
- **Precio de Pro: "A definir"** (elegido por el usuario): la UI no inventa un monto.
- **No hay endpoint para cambiar de plan.** Sin cobro, un endpoint así regalaría Pro. La suscripción
  avisa "todavía no está disponible" y no llama a la API. Lo que sí se escribe es lo que no regala
  nada: el guard y la UI.
- **El plan se decide en el backend, antes de validar.** Un Free recibe 403 aunque el ejercicio no
  exista o la consulta venga mal formada: no puede usar la API para sondear. Un `max` sin migrar
  se lee como `free` (`planSchema.catch('free')`): da menos, no más.
- **Bajar de Pro no borra nada.** Ejercicios y marcas quedan; sólo se deja de ver las estadísticas.
- **Sin lock para las altas.** Al irse el cupo, el serializador por usuario no tenía para qué; el
  índice único `user_exercise_unique` hace que la segunda alta del mismo ejercicio se deshaga y
  responda `WC-EXO-409-003`. Hay un test de integración contra un replica set.
- **Cortes de tarea cambiados sobre la marcha.** El backlog nació con "schemas / API / web" por
  separado, pero quitar `usage` del contrato rompe a las tres capas: no hay un commit verde sólo
  de schemas. F8-01 pasó a ser "se va el límite" en las tres a la vez, F8-02 el renombre y F8-03 la
  regla. Y la suscripción (F8-04) va antes que el bloqueo (F8-05) porque éste enlaza a ella.
- **Un control de plan sólo para el E2E.** Los E2E necesitan atletas de un plan y del otro y no hay
  endpoint ni pago. `dev:ephemeral` levanta un `POST /plan` en `127.0.0.1:3101` con su propia
  conexión; no existe en `server.ts` ni en lo que se despliega, y el script se niega con
  `NODE_ENV=production`. Se descartó sumar `mongodb` a `apps/web` (ya hubo un lockfile con dos
  copias).
- La suscripción **no está en el menú**: se llega desde el Perfil, desde la etiqueta PRO y desde el
  aviso de lo bloqueado (spec §5.5).

## Bloqueos / lo que no funcionó

- Los heredocs largos de Python en el shell fallaron varias veces ("unexpected EOF"): los scripts
  de edición pasaron a archivos escritos con `Write`, con un `assert` por reemplazo.
- `pnpm verify` falla en esta máquina con timeouts de 5 s y "Timed out waiting for a Primary" del
  replica set en memoria cuando corre los cuatro workspaces a la vez; solos, API (408) y web (392)
  pasan, y coverage también. Es carga, no lógica.
- El primer E2E de "bajar de plan" estaba mal armado: la caché de la pantalla conservaba las
  estadísticas de cuando era Pro y no volvía a pedirlas, así que no veía el 403. El caso real —la
  primera consulta después de que el plan cambió en otro dispositivo— se prueba pidiéndolas por
  primera vez después de bajar.
- `lint`: `z.string().email()` está deprecado (`z.email()`), y `as HTMLElement` y `!` se pelean
  entre sí en los tests: un helper que falla con un mensaje.
