# 2026-09-22 — F3-04: el build de producción de la API

- Autor: Claude Sonnet 5 (agente), con Braian
- Duración aprox: una sesión

## Objetivo

Lo que Railway corre, versionado y probado como código: build, migraciones antes del tráfico,
healthcheck correcto.

## Qué se hizo

- `.railway/railway.ts`, con el SDK oficial (`railway`, Infrastructure as Code — `railway.json` está
  deprecado y deja de leerse el 2026-12-01). Un servicio: `pnpm build`, `start: node
apps/api/dist/server.js`, `preDeploy: migrate:dist up`, `healthcheck: /ready`.
- `apps/api/src/deploy/railway-config.test.ts`: 15 tests sobre las dos configuraciones
  (`production` y `staging`) que da el archivo.
- README en `.railway/` con `plan`/`apply`, sin tocar ninguna cuenta.

## Decisiones tomadas

- **IaC y no Config as Code**: `railway.json` está deprecado, con corte duro el 2026-12-01. Empezar
  ahora con lo viejo sería deuda desde el día uno.
- **`/ready` como healthcheck, no `/health`**: con migraciones pendientes o sin Mongo, la instancia
  nueva no tiene que recibir tráfico aunque el proceso esté vivo. Probado a mano: sin migrar, 503.
- **Los secretos van con `preserve()`**: el archivo nunca los tiene; se cargan una vez en Railway.
- **`plan`/`apply` los corre el usuario**: es la parte 🔑 de F3-07, no de esta tarea. Esta tarea sólo
  entrega el archivo para revisar.

## Bloqueos / lo que no funcionó

- Nada. Siete pruebas inversas (rama, comando de arranque, sin migrar, healthcheck equivocado,
  secreto hardcodeado, staging con la base de prod, rate limit apagado) rompen un test cada una.
- Simulacro completo en local: `pnpm build`, `migrate:dist up`, `node apps/api/dist/server.js` con
  `NODE_ENV=production` contra un Mongo en memoria. `/ready` en 503 antes de migrar y en verde
  después; `/health` siempre en 200, que es la separación liveness/readiness que se buscaba.
