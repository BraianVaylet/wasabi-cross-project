# 2026-09-22 — F3-05: el build de producción del front

- Autor: Claude Opus 5.5 (agente), con Braian
- Duración aprox: una sesión

## Objetivo

Que el front compilado y servido por la API (ADR-0007) se comporte como tiene que comportarse en
producción, y que el E2E lo pruebe así en vez de contra el servidor de desarrollo.

## Qué se hizo

- La API pone la caché de lo que sirve: lo de `/assets/` (con hash en el nombre) un año e
  `immutable`; todo lo demás —el `index.html`, el service worker— `no-cache`.
- `pnpm e2e:prod` y `playwright.prod.config.ts`: la suite entera contra el build servido por la API,
  en el mismo origen. CI corre este modo.
- `e2e/produccion.spec.ts`, cuatro tests que sólo tienen sentido ahí: una ruta de la SPA pedida de
  cero, la caché, el service worker registrándose, y la consola sin errores.

## Decisiones tomadas

- **Dos configs que comparten una función**, en vez de una variable de entorno: `cross-env` no está
  y no valía una dependencia. Los specs de producción se saltan mirando la metadata de la config.
- **El modo desarrollo sigue siendo el de `pnpm e2e`**: el que se corre a mano mientras se programa.
  CI corre el de producción, que es el que ve un atleta.
- **Caché por carpeta y no por nombre**: todo `/assets/` lo genera Vite con hash. Lo que está en la
  raíz se revalida siempre, aunque alguno (el de workbox) tenga hash: es un poco menos eficiente y
  nunca se equivoca.

## Bloqueos / lo que no funcionó

- Para no fabricar un conflicto con #39, que también cambia `playwright.config.ts`, la rama trae a
  #39 adentro. La PR apunta a `main` y se achica sola cuando entren las anteriores.
- El service worker que en F3-03 no registraba en el navegador embebido, en el Chromium de
  Playwright registra: era el panel, como se sospechaba.
- `@fastify/static` 10 le pasa a `setHeaders` el `reply` de Fastify, no la respuesta cruda: el
  primer intento con `setHeader` colgaba los pedidos.
